## Теория

Индекс в PostgreSQL — это отдельная структура данных, которая хранит значения одного или нескольких столбцов и ссылки на строки таблицы. Индекс нужен для ускорения поиска, фильтрации, сортировки, соединения таблиц и проверки уникальности. Цена индекса — дополнительное место на диске и замедление `INSERT`, `UPDATE`, `DELETE`, потому что при изменении таблицы PostgreSQL должен обновлять не только данные, но и все связанные индексы.

Основные типы индексов PostgreSQL:

- `B-tree` — индекс по умолчанию. Подходит для `=`, `<`, `>`, `<=`, `>=`, `BETWEEN`, `ORDER BY`, `MIN`, `MAX`, префиксного `LIKE 'abc%'` при подходящих настройках/операторных классах. Самый универсальный тип.
- `Hash` — подходит для точного сравнения `=`, но обычно используется реже, потому что `B-tree` тоже хорошо работает для равенства и поддерживает больше операций.
- `GIN` — инвертированный индекс. Используется для полнотекстового поиска, массивов, `jsonb`, а также для триграммного поиска через расширение `pg_trgm`. Хорошо подходит для `LIKE '%text%'` и `ILIKE '%text%'`.
- `GiST` — обобщенный индекс для геометрии, диапазонов, полнотекстового поиска и специальных типов данных. Подходит, когда данные сравниваются не только по равенству, но и по пересечению, близости, включению.
- `BRIN` — блочно-диапазонный индекс. Эффективен для очень больших таблиц, где значения физически упорядочены или близки к порядку вставки, например даты событий в журнале.
- `SP-GiST` — индекс для данных, которые удобно разбивать на непересекающиеся области: точки, префиксные деревья, некоторые геометрические структуры.

Селективность — доля строк, которую отбирает условие. Чем меньше строк возвращает фильтр, тем выгоднее индекс. Например, `status = 'cancelled'`, если таких строк 5%, может быть полезнее для индекса, чем `total_price > 0`, если условие истинно почти для всех строк.

Кардинальность — количество разных значений в столбце. Столбцы с высокой кардинальностью обычно лучше подходят для индексов. Например, `booking_id`, `created_at`, `property_id` полезнее для поиска, чем булевый `is_active`, если значения распределены почти поровну или одно значение сильно доминирует.

Составной индекс строится по нескольким столбцам. Важен порядок колонок. Обычно первыми ставят условия точного сравнения, затем диапазоны и колонки сортировки. Индекс `(property_id, status, check_in_date)` хорошо работает для `property_id = ... AND status = ... AND check_in_date >= ...`.

Покрывающий индекс позволяет выполнить запрос с меньшим числом обращений к таблице, если все нужные поля есть в индексе. В PostgreSQL для этого можно использовать `INCLUDE`.

Частичный индекс строится только по части строк, например `WHERE status = 'confirmed'`. Он меньше полного индекса и быстрее для запросов, которые используют то же условие.

`EXPLAIN` показывает план, который PostgreSQL выбрал для запроса. `EXPLAIN ANALYZE` не только строит план, но и реально выполняет запрос, поэтому показывает фактическое время, количество строк и отклонения между оценкой планировщика и реальностью. Опция `BUFFERS` показывает работу с блоками памяти и диска.

Частые узлы плана:

- `Seq Scan` — последовательное чтение таблицы. Нормально для маленьких таблиц или низкоселективных условий.
- `Index Scan` — чтение через индекс с обращением к таблице за строками.
- `Index Only Scan` — чтение только из индекса, если все нужные данные есть в индексе и карта видимости позволяет не читать таблицу.
- `Bitmap Index Scan` + `Bitmap Heap Scan` — сначала собираются подходящие ссылки из индекса, потом пачками читаются страницы таблицы. Часто используется, когда найдено не несколько строк, а заметная часть таблицы.
- `Sort` — отдельная сортировка. Если индекс уже хранит данные в нужном порядке, этот узел может исчезнуть.
- `Hash Join`, `Nested Loop`, `Merge Join` — разные алгоритмы соединения таблиц.

Статистика влияет на выбор плана. После массовой загрузки данных и создания индексов нужно выполнять `ANALYZE`, чтобы планировщик знал распределение значений и мог оценить селективность условий.

Индекс может не использоваться, если запрос возвращает большую часть таблицы, если условие имеет низкую селективность, если статистика устарела, если выражение в запросе не совпадает с выражением индекса, или если последовательное чтение дешевле случайного доступа по индексу.

## Сценарий 1. Сложный фильтр

SQL-запрос:

```sql
SELECT COUNT(*), SUM(total_price)
FROM bookings
WHERE status = 'confirmed'
  AND check_in_date BETWEEN DATE '2025-06-01' AND DATE '2025-12-31'
  AND total_price BETWEEN 500 AND 2000;
```

Гипотеза: без индекса PostgreSQL будет читать большую часть `bookings`, потому что фильтр применяется к таблице из `1 000 000` строк. Составной B-tree индекс по `status`, `check_in_date`, `total_price` должен ускорить выборку: `status` используется как точное сравнение, `check_in_date` и `total_price` как диапазоны.

Индекс:

```sql
CREATE INDEX idx_lab4_bookings_complex_filter
ON bookings (status, check_in_date, total_price);
```

## Сценарий 2. Сортировка с ограничением

SQL-запрос:

```sql
SELECT booking_id, guest_id, property_id, status, created_at, total_price
FROM bookings
WHERE status IN ('confirmed', 'pending')
ORDER BY created_at DESC
LIMIT 20;
```

Гипотеза: без индекса PostgreSQL должен отобрать строки, отсортировать их по `created_at DESC` и вернуть первые 20. Индекс по `created_at DESC` позволяет читать строки сразу в нужном порядке и остановиться после нахождения 20 подходящих записей.

Индекс:

```sql
CREATE INDEX idx_lab4_bookings_created_at_desc
ON bookings (created_at DESC);
```

## Сценарий 3. Альтернативные варианты индексирования

SQL-запрос:

```sql
SELECT COUNT(*), SUM(total_price)
FROM bookings
WHERE property_id = 2494
  AND status = 'confirmed'
  AND check_in_date >= DATE '2025-01-01';
```

Гипотеза: запрос можно ускорить двумя составными индексами, но порядок колонок влияет на эффективность. Индекс `(property_id, status, check_in_date)` должен быть лучше, если `property_id` более селективен, чем `status`. Индекс `(status, property_id, check_in_date)` тоже применим, но сначала отталкивается от менее селективного признака.

Индексы:

```sql
CREATE INDEX idx_lab4_bookings_property_status_date
ON bookings (property_id, status, check_in_date);

CREATE INDEX idx_lab4_bookings_status_property_date
ON bookings (status, property_id, check_in_date);
```

## Сценарий 4. Текстовый поиск

SQL-запрос:

```sql
SELECT property_id, title, city, price_per_night
FROM properties
WHERE title ILIKE '%Villa%'
   OR description ILIKE '%sea view%'
   OR title ILIKE 'Central%'
   OR title ILIKE '%777';
```

Гипотеза: обычный B-tree плохо подходит для поиска подстроки и суффикса, особенно когда шаблон начинается с `%`. Расширение `pg_trgm` и GIN-индексы позволяют искать по триграммам и ускоряют `ILIKE '%...%'`, `ILIKE '...%'` и `ILIKE '%...'`.

Индексы:

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE INDEX idx_lab4_properties_title_trgm
ON properties USING gin (title gin_trgm_ops);

CREATE INDEX idx_lab4_properties_description_trgm
ON properties USING gin (description gin_trgm_ops);
```

План после оптимизации: вставить вывод из `lab4/05_explain_after.sql`.

## Сценарий 5. JOIN

SQL-запрос:

```sql
SELECT p.property_id, p.title, h.email, COUNT(b.booking_id), SUM(b.total_price)
FROM properties p
JOIN users h ON h.user_id = p.host_id
JOIN bookings b ON b.property_id = p.property_id
WHERE p.city = 'Paris'
  AND b.status = 'confirmed'
  AND b.check_in_date >= DATE '2025-01-01'
GROUP BY p.property_id, p.title, h.email
ORDER BY SUM(b.total_price) DESC
LIMIT 20;
```

Гипотеза: узкое место — большая таблица `bookings`, которая соединяется с `properties`. Индекс `(status, check_in_date, property_id)` помогает сначала отобрать подтвержденные бронирования за нужный период, а затем быстрее соединить их с объектами жилья по `property_id`.

Индекс:

```sql
CREATE INDEX idx_lab4_bookings_join_status_property
ON bookings (status, check_in_date, property_id);
```

План до оптимизации: вставить вывод из `lab4/03_explain_before.sql`.

## Сценарий 6. Негативный сценарий

SQL-запрос:

```sql
SELECT COUNT(*)
FROM bookings
WHERE total_price > 0;
```

Гипотеза: индекс по `total_price` почти не поможет, потому что условие истинно для всех строк из-за ограничения `CHECK (total_price > 0)`. PostgreSQL может выбрать последовательное сканирование, так как чтение всей таблицы дешевле, чем обход индекса и обращение к большому числу строк.

Индекс:

```sql
CREATE INDEX idx_lab4_bookings_total_price
ON bookings (total_price);
```

## Влияние индексов на INSERT и UPDATE

Для проверки используется `lab4/06_insert_update_impact.sql`. Скрипт сначала удаляет дополнительные индексы лабораторной, затем замеряет `INSERT` и `UPDATE`, после этого создает индексы и повторяет те же операции.

Ожидаемый результат:

| Операция | Без дополнительных индексов | С индексами |
|---|---:|---:|
| INSERT 20 000 строк | заполнить | заполнить |
| UPDATE 20 000 строк | заполнить | заполнить |

Вывод: при наличии индексов изменение данных обычно выполняется медленнее. Это связано с тем, что PostgreSQL должен поддерживать актуальность каждой индексной структуры. Поэтому индексы нужно создавать под реальные частые запросы, а не на все столбцы подряд.

## Общий вывод

Индексы дают максимальный эффект, когда условия запроса селективны, порядок колонок соответствует структуре фильтра, а тип индекса соответствует операции. B-tree подходит для равенства, диапазонов и сортировки. GIN с `pg_trgm` подходит для поиска подстрок. Для запросов, которые возвращают большую часть таблицы, индекс может не использоваться и не давать заметного прироста. Индексирование ускоряет чтение, но увеличивает стоимость вставки и обновления строк.
