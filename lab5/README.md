# Лабораторная работа №5. Исследование транзакций в PostgreSQL

## Цель

Исследовать работу транзакций в PostgreSQL: фиксацию изменений, откат, точки сохранения, блокировки, аномалии параллельного выполнения и уровни изоляции.

## Используемая база данных

Используется схема сервиса бронирования жилья из лабораторной работы №1:

- `users` — пользователи;
- `property_types` — типы жилья;
- `properties` — объекты жилья;
- `bookings` — бронирования;
- `reviews` — отзывы.

Для лабораторной выбраны три бизнес-сценария:

- создание завершенного бронирования и отзыва;
- отмена бронирования и изменение состояния объекта жилья;
- изменение статуса хоста и связанных объектов жилья.

Во всех сценариях данные изменяются в нескольких связанных таблицах, поэтому операции должны выполняться атомарно.

## Теория

Транзакция — это группа SQL-операций, которая выполняется как единое целое. Если все операции успешны, изменения фиксируются командой `COMMIT`. Если произошла ошибка или бизнес-правило нарушено, изменения отменяются командой `ROLLBACK`.

Главные свойства транзакций описываются ACID:

- `Atomicity` — атомарность: выполняется все или ничего.
- `Consistency` — согласованность: база переходит из одного корректного состояния в другое.
- `Isolation` — изолированность: параллельные транзакции не должны некорректно влиять друг на друга.
- `Durability` — долговечность: после `COMMIT` данные сохраняются даже при сбое.

`SAVEPOINT` — точка сохранения внутри транзакции. Она позволяет откатить только часть операций через `ROLLBACK TO SAVEPOINT`, не отменяя всю транзакцию.

Сессия — отдельное подключение клиента к PostgreSQL. В DBeaver одна вкладка может использовать то же соединение, что и другая, поэтому для демонстрации параллельности важно открыть две независимые сессии. Независимые сессии имеют разные транзакции, разные снимки данных и могут блокировать друг друга.

Снимок данных — представление базы, которое видит транзакция. На `READ COMMITTED` новый снимок создается для каждого SQL-оператора. На `REPEATABLE READ` и `SERIALIZABLE` снимок фиксируется на уровне транзакции.

Блокировка — механизм PostgreSQL, который защищает данные от конфликтующих параллельных изменений. Например, если одна транзакция обновила строку и еще не сделала `COMMIT`, другая транзакция при попытке обновить ту же строку будет ждать освобождения блокировки.

Основные блокировки, которые важны для этой лабораторной:

- строковая блокировка появляется при `UPDATE`/`DELETE` конкретной строки и удерживается до конца транзакции;
- табличные блокировки берутся автоматически для защиты структуры таблицы и согласования операций;
- `lock_timeout` ограничивает время ожидания блокировки и помогает явно увидеть конфликт в учебном примере.

Уровни изоляции:

- `READ COMMITTED` — уровень по умолчанию. Каждый SQL-запрос внутри транзакции видит только зафиксированные данные на момент начала этого конкретного запроса. Возможны неповторяющиеся чтения.
- `REPEATABLE READ` — транзакция видит снимок данных на момент начала транзакции. Повторное чтение тех же строк дает тот же результат, даже если другая транзакция уже изменила и зафиксировала данные.
- `SERIALIZABLE` — самый строгий уровень. PostgreSQL пытается выполнить параллельные транзакции так, как будто они выполнялись последовательно. При конфликте одна транзакция может завершиться ошибкой сериализации.

Типичные аномалии:

- `Dirty read` — чтение незафиксированных данных другой транзакции. В PostgreSQL не допускается.
- `Non-repeatable read` — повторное чтение строки в одной транзакции дает другой результат. Возможно на `READ COMMITTED`.
- `Phantom read` — повторный запрос по условию возвращает новый набор строк из-за вставок другой транзакции.
- `Lost update` — потеря обновления, когда две транзакции перезаписывают результат друг друга.
- `Serialization failure` — конфликт на `SERIALIZABLE`, когда PostgreSQL отклоняет одну транзакцию для сохранения корректности.

PostgreSQL не допускает `dirty read` даже если указать `READ UNCOMMITTED`: фактически этот уровень работает как `READ COMMITTED`.

Ошибки внутри транзакций важны практически. Если ошибка не обработана, транзакция переходит в состояние aborted, и до `ROLLBACK` большинство команд выполнять нельзя. В сценариях лабораторной ошибка моделируется внутри блока `DO ... EXCEPTION`, чтобы показать причину ошибки и затем явно выполнить полный `ROLLBACK`.

## Сценарий 1. Создание завершенного бронирования и отзыва

Бизнес-смысл: гость завершил проживание, система создает запись о бронировании и отзыв. Эти изменения должны быть согласованы: отзыв не должен появиться без бронирования.

Файл: `lab5/02_scenario_booking_review.sql`.

Успешная транзакция:

- создается запись в `bookings` со статусом `completed`;
- создается связанная запись в `reviews`;
- выполняется `COMMIT`;
- проверочный `SELECT` показывает бронирование и отзыв.

Ошибка и полный откат:

- создается бронирование;
- моделируется ошибка при создании отзыва с рейтингом `9`;
- ошибка перехватывается;
- выполняется `ROLLBACK`;
- проверка показывает, что бронирование не сохранилось.

Точка сохранения:

- создается бронирование;
- создается `SAVEPOINT before_optional_review`;
- добавляется черновой отзыв;
- выполняется `ROLLBACK TO SAVEPOINT`;
- добавляется исправленный отзыв;
- выполняется `COMMIT`.

Вывод: транзакция гарантирует, что бронирование и отзыв фиксируются согласованно, а `SAVEPOINT` позволяет откатить только ошибочную часть операции.

## Сценарий 2. Отмена бронирования и изменение объекта жилья

Бизнес-смысл: при отмене бронирования система меняет статус бронирования и может изменить состояние объекта жилья.

Файл: `lab5/03_scenario_cancel_booking.sql`.

Успешная транзакция:

- бронирование переводится в статус `cancelled`;
- объект жилья становится неактивным;
- выполняется `COMMIT`.

Ошибка и полный откат:

- бронирование переводится в `cancelled`;
- моделируется ошибка: цена объекта устанавливается в отрицательное значение;
- ограничение `CHECK (price_per_night > 0)` не позволяет выполнить изменение;
- выполняется `ROLLBACK`;
- статус бронирования и цена остаются прежними.

Точка сохранения:

- бронирование переводится в `cancelled`;
- создается `SAVEPOINT before_property_deactivation`;
- объект временно деактивируется;
- выполняется частичный откат к точке сохранения;
- вместо деактивации изменяется цена;
- выполняется `COMMIT`.

Вывод: полный откат защищает данные от частично выполненной отмены, а точка сохранения позволяет поменять решение внутри одной транзакции.

## Сценарий 3. Изменение хоста и связанных объектов

Бизнес-смысл: при изменении состояния хоста нужно согласованно обновить данные пользователя и его объектов жилья.

Файл: `lab5/04_scenario_host_property_update.sql`.

Успешная транзакция:

- хост помечается как неподтвержденный;
- связанные объекты жилья деактивируются;
- выполняется `COMMIT`.

Ошибка и полный откат:

- у хоста меняется телефон;
- моделируется ошибка: у его объектов устанавливается `max_guests = 0`;
- ограничение `CHECK (max_guests > 0)` отклоняет изменение;
- выполняется `ROLLBACK`;
- телефон и объекты остаются в исходном состоянии.

Точка сохранения:

- меняется телефон хоста;
- создается `SAVEPOINT before_price_discount`;
- применяется слишком большой временный дисконт;
- выполняется частичный откат;
- вместо дисконта обновляется описание объекта;
- выполняется `COMMIT`.

Вывод: связанные изменения пользователя и объектов должны выполняться в одной транзакции, иначе можно получить несогласованное состояние.

## Параллельные транзакции и блокировки

Для этого блока нужно открыть две вкладки SQL Editor.

Блокировка строки:

1. В первой вкладке запустить `lab5/05_lock_session_a.sql`.
2. Пока первая вкладка выполняет `pg_sleep(30)`, во второй вкладке запустить `lab5/06_lock_session_b.sql`.
3. Вторая транзакция попытается обновить ту же строку `properties.property_id = 1`.
4. Из-за `lock_timeout = '5s'` вторая транзакция должна получить ошибку ожидания блокировки.

Вывод: первая транзакция удерживает блокировку измененной строки до `COMMIT`, поэтому вторая транзакция не может изменить эту же строку одновременно.

## READ COMMITTED и REPEATABLE READ

Для сравнения нужно использовать две вкладки.

READ COMMITTED:

1. В первой вкладке запустить `lab5/07_read_committed_session_a.sql`.
2. Пока первая вкладка выполняет `pg_sleep(30)`, во второй вкладке запустить `lab5/09_isolation_session_b_update.sql`.
3. В первой вкладке первое и второе чтение могут показать разные значения `price_per_night`.

Вывод: на `READ COMMITTED` каждый запрос видит новый снимок уже зафиксированных данных, поэтому возможно неповторяющееся чтение.

REPEATABLE READ:

1. Заново выполнить `lab5/01_prepare_data.sql`, чтобы вернуть исходные данные.
2. В первой вкладке запустить `lab5/08_repeatable_read_session_a.sql`.
3. Пока первая вкладка выполняет `pg_sleep(30)`, во второй вкладке запустить `lab5/09_isolation_session_b_update.sql`.
4. В первой вкладке первое и второе чтение должны показать одно и то же значение.

Вывод: на `REPEATABLE READ` транзакция видит один снимок данных до завершения, поэтому повторное чтение стабильно.

## SERIALIZABLE

Для демонстрации конфликта:

1. Заново выполнить `lab5/01_prepare_data.sql`.
2. В первой вкладке запустить `lab5/10_serializable_session_a.sql`.
3. Пока первая вкладка выполняет `pg_sleep(30)`, во второй вкладке запустить `lab5/11_serializable_session_b.sql`.
4. Одна из транзакций может завершиться ошибкой сериализации.

Смысл конфликта: обе транзакции проверяют, что на объект `property_id = 3` нет подтвержденного бронирования на `2028-02-01`, и обе пытаются вставить бронирование. На уровне `SERIALIZABLE` PostgreSQL должен предотвратить некорректное параллельное выполнение.

Вывод: `SERIALIZABLE` повышает корректность параллельного выполнения, но может требовать повторного запуска транзакции при ошибке сериализации.

## Общий вывод

Транзакции позволяют выполнять связанные изменения атомарно. `COMMIT` фиксирует корректный набор изменений, `ROLLBACK` полностью отменяет неудачную операцию, а `SAVEPOINT` дает возможность откатить только часть действий. При параллельном доступе PostgreSQL использует блокировки и уровни изоляции. `READ COMMITTED` допускает неповторяющиеся чтения, `REPEATABLE READ` сохраняет стабильный снимок данных, а `SERIALIZABLE` предотвращает опасные параллельные аномалии ценой возможных конфликтов сериализации.
